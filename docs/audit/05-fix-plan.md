# 5) خطة الإصلاح المرتبة

**قاعدة عامة:** لا إصلاح بدون (أ) اختبار يُثبت المشكلة أولًا، (ب) تغيير صغير في فرع مستقل وPR مستقل، (ج) نفس الاختبار ينجح بعده، (د) موافقتك قبل أي تأثير على الإنتاج.

## المرحلة 0 — بنية المراجعة (قبل أي إصلاح)

| الخطوة | الدليل المطلوب لإغلاقها |
|---|---|
| 0.1 حماية `main` (PR إلزامي + نجاح الفحوص) | لقطة إعدادات Rules |
| 0.2 اعتماد `ci.yml` وقالب PR | أول تشغيل أخضر/أحمر على الفرع يوثّق حالة البناء الحقيقية |
| 0.3 مشروع Supabase اختبار منفصل + متغيراته في Vercel لبيئة Preview فقط | قائمة المتغيرات + إثبات أن Preview يقرأ قاعدة الاختبار |
| 0.4 طبّق `supabase/schema.sql` ثم migrations بالترتيب على قاعدة الاختبار | سجل التطبيق بلا أخطاء؛ ثم قارن مع الإنتاج |
| 0.5 قارن الإنتاج بالمستودع (قراءة فقط): `list_migrations` وسياسات الجداول | جدول "طُبّق/لم يُطبّق" لكل migration |

## المرحلة 1 — P0 (كل بند: اختبار يفشل ← إصلاح ← ينجح)

| # | الإصلاح المقترح | اختبار الإثبات |
|---|---|---|
| R1 | إزالة القيم الاحتياطية وجعل البناء يفشل بوضوح إن غابت المتغيرات | بناء بلا `.env` يفشل برسالة؛ Preview لا يصل للإنتاج |
| R2 | تقييد INSERT على `requests`: `assigned_to`/`customer_id` فارغان للمجهول، `type` ضمن قائمة، ومخطط `payload`؛ وإزالة cast الـ UUID الخطر | INSERT مجهول بقيم متلاعبة يُرفض؛ طلب مشوّه لا يعطّل استعلام شريك |
| R3 | توسيع trigger الحماية (`status`, `payload.partnerId`) حسب الدور، وتقييد تعديل الموظفين وقراءة الملاحظات بنفس نطاق SELECT | مصفوفة أدوار × عمليات (عميل/شريك/كل مدير) على بيانات اختبار |
| R4 | `TO authenticated` + شرط ملكية على جداول التاريخ والإشعارات، أو نقل الكتابة إلى triggers | INSERT مجهول يُرفض |
| R5 | حصر أعمدة `partners` العامة (view عام بالأعمدة الآمنة أو `GRANT` بالأعمدة) | `select=*` بمفتاح anon لا يُرجع email/role/custom_permissions |

## المرحلة 2 — P1

R6 (توحيد الـ migrations: ترقيم فريد + `supabase/config.toml` + تحديد خط الأساس)، R7 (اختبار سلبي للتسجيل المرتفع)، R9 (فحص الحزمة بعد البناء وإزالة بيانات `data/` التجريبية من مسار الإنتاج)، R10 (rate limit وتوحيد نسخة credentials)، R11.

## المرحلة 3 — نظافة

- استعادة/حذف الملفات التالفة (`.vercelignore`, `schema.prisma`, `supabase_schema.sql`) وقرار صريح: حذف Prisma نهائيًا أم إعادته.
- إضافة lockfile، وتفعيل قواعد ESLint فعلية.
- تحديث `README.md` ليصف الواقع، وأرشفة `BACKEND_BLUEPRINT.md` و`DEVELOPMENT_PLAN.md` والـ `tar.gz` و`.aistudio/`.

## ما لا يُفعل الآن

لا ميزات جديدة، ولا حذف جماعي لملفات SQL (`scripts/cleanup*.sh` من الـ ZIP القديم تحذف ملفات `db_*.sql` ولا تُشغَّل)، ولا أي تغيير بنيوي (استبدال Supabase أو Prisma أو الراوتر) قبل إغلاق المرحلتين 0 و1.
